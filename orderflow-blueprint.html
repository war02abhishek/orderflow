System design — v3

OrderFlow Blueprint

A flash-sale checkout platform used as a hands-on lab for distributed-systems scale: what's already covered by the build plan, and where it falls short of an actually scalable, consistent, fault-tolerant, available system.

Cluster local kind, 1 control-plane + 2 workers Mesh Istio Services orders · inventory · payment · notifications Stack Spring Boot · Postgres · Kafka · Redis (targeted use only)

Architecture overview

Four namespaced services behind an Istio ingress gateway, one synchronous hop (stock reservation), and one asynchronous backbone (Kafka) carrying the payment saga and its downstream notifications.

The checkout saga

Stock reservation is synchronous and blocking — checkout needs to know immediately if the item exists. Everything downstream of a successful reservation is an orchestrated saga over Kafka, with a compensating action if payment fails. 

sequenceDiagram
  participant C as Client
  participant O as orders
  participant I as inventory
  participant DB as orders DB (outbox)
  participant K as Kafka
  participant P as payment
  participant N as notifications

  C->>O: POST /checkout
  O->>I: reserve(sku, qty)  [sync]
  I-->>O: reserved

  O->>DB: INSERT Order(AWAITING_PAYMENT)\n+ outbox row: PaymentRequested  (1 txn)
  O->>K: relay publishes PaymentRequested
  K->>P: consume PaymentRequested

  alt payment succeeds
    P->>K: publish PaymentCompleted
    K->>O: consume result
    O->>DB: Order -> CONFIRMED\n+ outbox row: OrderPlaced
    O->>K: relay publishes OrderPlaced
    K->>N: consume OrderPlaced
    N-->>C: confirmation sent
  else payment fails
    P->>K: publish PaymentFailed
    K->>O: consume result
    O->>I: release(sku, qty)  [compensating, sync]
    O->>DB: Order -> CANCELLED\n+ outbox row: OrderCancelled
    O->>K: relay publishes OrderCancelled
    K->>N: consume OrderCancelled
    N-->>C: cancellation sent
  end

The outbox row and the order-state change commit in one local transaction — the Kafka publish can never be lost or fabricated relative to that state.

Where Redis fits — and where it doesn't

Not added by default. Two places in this system have a genuine job for it; everywhere else, adding it would either do nothing or reintroduce a race the design already closes.

Earns its place
  • Idempotency fast-path (G17, and G2's implementation). inventory's /reserve//release and payment's Kafka consumer both need to recognize "already handled this one" — on an Istio retry, or on a redelivered message after a consumer-group rebalance. A Redis SETNX-with-TTL check answers that in under a millisecond without touching Postgres. Postgres still holds a unique constraint on the same key as the durable backstop, so a Redis restart never silently reopens a closed door — Redis just saves the round-trip on the common case, on the exact database that's already a named SPOF (G6) during the highest-traffic moment.
  • Shared rate-limit counters (G18) — only if it matters. Once the ingress gateway runs 2+ replicas (G14), an Envoy local rate limit is enforced per-replica: the effective ceiling becomes roughly limit × replica count, not the configured number. If a precise global limit matters, Envoy's Rate Limit Service backed by Redis as the shared counter store is the standard fix. If "roughly N× replicas, still sheds load before the system falls over" is good enough for a learning cluster, this is skippable — see G18 below, presented as a choice, not a mandate.
Not needed here
  • Caching the inventory stock count for the reservation decision. The reservation has to read the live value at write time — that's the entire point of G1's atomic conditional update. A cache in front of that path reintroduces the stale-read race G1 exists to close.
  • A stock/catalog read cache. Legitimate pattern in general — but there's no catalog/browse endpoint in this system (no "show approximate stock while shopping" read path) for it to sit in front of. Worth adding if that endpoint ever exists; not before.
  • Pub/sub fan-out. No real-time/WebSocket surface here — nothing to fan out to multiple pods, unlike a chat/matchmaking system.

Four pillars: what's covered, what's missing

Scalability, consistency, fault tolerance, and availability pull against each other, so each gets checked on its own terms rather than assumed from "we used Kubernetes and a mesh."

Scalability

throughput under load
Already in the plan
  • HPA on orders, replicas load-balanced via ClusterIP + kube-proxy
  • Stateless services — any replica can serve any request
  • Async hop via Kafka absorbs bursty/slow downstream work
Gaps
  • Kafka topics default to 1 partition — payment and notifications can't scale consumers horizontally without more partitions (G4)
  • No rate limiting at the edge — HPA reacts in seconds, a 10x spike arrives in one (G13)
  • Once the ingress gateway is HA (G14), a per-replica rate limit quietly becomes "limit × replica count" instead of the configured number (G18)

Consistency

correctness across services
Already in the plan
  • Outbox pattern makes the DB-write-plus-publish step atomic
  • Saga gives an explicit, inspectable state machine per order
Gaps
  • Overselling: concurrent reservations against the same SKU during a flash sale can both read "in stock" before either writes — needs an atomic conditional update, not read-then-write (G1)
  • Istio's own retry policy on orders → inventory can re-send a reservation call — /reserve and /release must be idempotent or a retry double-reserves (G2)
  • A Kafka consumer-group rebalance can redeliver a message payment or notifications already processed — those consumers aren't idempotent yet, only the REST calls are (G17)
  • No documented consistency model — which parts are strongly consistent (a service's own transaction) vs. eventually consistent (across the saga) is implicit, not written down (G16)

Fault tolerance

surviving a component failing
Already in the plan
  • Istio retries/timeouts/circuit-breaking on the inventory call
  • Multi-node kind cluster — pods can spread across nodes
Gaps
  • Single-broker Kafka is a hard single point of failure — no replication factor possible with one broker (G7)
  • Shared single Postgres instance is a SPOF for three services at once (G6)
  • No dead-letter topic — one malformed message can wedge a consumer indefinitely (G5)
  • No pod anti-affinity — nothing stops all replicas of a service landing on the same node (G9)

Availability

staying reachable during change
Already in the plan
  • Canary rollout limits blast radius of a bad deploy
  • Multiple replicas behind a Service already give redundancy
Gaps
  • No readiness/liveness probes — K8s can't tell a hung pod from a healthy one, or hold traffic until warm-up finishes (G8)
  • No resource requests/limits — scheduler placement and HPA's CPU% are both undefined without them (G10)
  • No PodDisruptionBudget — a node drain or rolling update can take every replica of a service down at once (G11)
  • No graceful shutdown handling — in-flight requests and outbox work can be cut mid-write on pod termination (G12)

The circuit breaker, as a state machine

What Istio's DestinationRule outlier detection actually does to the orders → inventory call, mapped onto the classic circuit-breaker states. 

stateDiagram-v2
  [*] --> Closed
  Closed --> Closed: request succeeds
  Closed --> Open: consecutive 5xx reaches threshold
  Open --> Open: new requests fail fast, host ejected from LB pool
  Open --> HalfOpen: ejection window elapses
  HalfOpen --> Closed: trial request succeeds
  HalfOpen --> Open: trial request fails

Ejection is per-host, not per-service — with 3 inventory replicas, one tripped host doesn't stop the other two from serving.

CAP trade-off, per hop

"This system is AP" or "this system is CP" is the wrong question — the answer differs by which call you're looking at. Under a network partition, here's what each hop actually gives up.

InteractionFavorsWhy
orders → inventory (sync reserve)ConsistencyMust know the real stock level right now; if inventory is unreachable, checkout fails fast rather than guessing and risking oversell
inventory's stock row itselfConsistencyAtomic conditional update, single row — no eventual state allowed here, that's the entire point of G1
orders → payment (saga, via Kafka)AvailabilityIf payment is unreachable, the order sits AWAITING_PAYMENT rather than blocking or failing outright — resolved later by the saga
orders → notifications (via Kafka)AvailabilityA notification can lag arbitrarily; it never blocks order completion
Kafka replication (RF 3, min.insync.replicas=2)ConsistencyTolerates losing 1 broker with zero data loss and no write pause; losing 2 blocks writes rather than silently accepting them unsafely
Rate limiting at the ingress (G13/G18)AvailabilityIndividual requests are sacrificed (429) specifically to keep the rest of the system responsive

What's strong, what's eventual

Strong consistency exists only inside a single service's own transaction: an order's state change and its outbox row commit together, atomically, inside orders' database. Same for inventory's stock decrement once G1 is fixed.

Everything across services is eventually consistent. Between "payment requested" and "payment resolved," an order legitimately sits in AWAITING_PAYMENT — that's not a bug, it's the saga doing its job. This system chooses availability over immediate consistency during a downstream partition, and recovers correctness later via the saga's compensation path. docs/07-saga-and-outbox.md should say this in those words — it's the one paragraph that explains the whole architecture's CAP trade-off.

What this changes in the roadmap

No new phases — these fold into the existing eight. The plan file should be updated to reflect this before implementation starts.

Phase 1

Add: atomic stock update (G1), idempotency key + dedup (G2), Actuator-backed readiness/liveness probes (G8), resource requests/limits (G10), pod anti-affinity (G9), graceful shutdown config (G12).

Phase 2

Add: 3-broker Kafka via Strimzi with replication factor 3 (G7), 3+ partitions on saga topics (G4), idempotent/acks=all outbox producer (G3), dead-letter topics (G5), trace-ID propagation via headers (G15), explicit consistency-model writeup (G16), idempotent Kafka consumers for `payment`/`notifications` backed by Redis + a Postgres unique-constraint backstop (G17), `CooperativeStickyAssignor` on all consumer groups.

Phase 4

Add: istiod + ingress gateway at 2+ replicas (G14), PodDisruptionBudgets alongside the resilience testing already planned (G11).

Phase 6

Add: Istio rate limiting at the edge as a companion to HPA, so the flash-sale story includes deliberate degradation, not just scaling (G13). Verify partitioned consumers (G4) actually scale out under the same load test, and consciously decide whether the per-replica rate limit needs to become a true global limit via Redis-backed RLS (G18) or stays a documented approximation.

Phase 8

Add: Postgres primary + replica, or per-service instances, as the remaining named SPOF (G6) — correctly scoped as a stretch given local kind resource limits.
