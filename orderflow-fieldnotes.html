01

What a cluster and a node actually are

Before anything else: Kubernetes doesn't run your code directly. It schedules your code onto nodes — machines (real or virtual) that actually have CPU/memory to give — and a cluster is just "a control plane plus a set of nodes it's in charge of."

On a real cloud, a node is a VM. Here, on a laptop, kind ("Kubernetes IN Docker") fakes that by making each node an ordinary Docker container that happens to run a full kubelet + container runtime inside it. So the "cluster" is, physically, four Docker containers talking to each other over a Docker network:

docker ps
orderflow-control-plane   — runs the API server, scheduler, etcd
orderflow-worker          — runs actual application pods
orderflow-worker2         — runs actual application pods
kind-registry              — the local image registry, not a cluster node

The control plane is the "brain": it stores desired state (etcd), decides which node a pod should land on (scheduler), and exposes the API everything else talks to (kubectl included). It doesn't usually run your application containers itself. Worker nodes are where pods actually execute.

Why 3 nodes specifically (1 control-plane + 2 workers)

Why

With only 1 worker, every pod has nowhere else to go — you can't observe "spread across nodes" because there's only one destination. 2 workers is the minimum that makes node placement a real decision instead of a foregone conclusion.

What it lets us see

3 replicas of inventory across 2 worker nodes landed 2-on-one-node, 1-on-the-other — a genuine scheduling decision, not a coincidence, and the exact scenario pod anti-affinity (G9) is about.

kubectl -n inventory get pods -o wide
inventory-8675bffd8-lr5h6   Running   192.168.198.133   orderflow-worker
inventory-8675bffd8-pm26w   Running   192.168.47.132    orderflow-worker2
inventory-8675bffd8-xcd66   Running   192.168.47.131    orderflow-worker2
02

The image registry

Kubernetes never builds code. Every Deployment says "run this exact image" — so the image has to exist somewhere pullable before any pod can start.

Why local, not Docker Hub

Pushing every build to a public registry just to test a one-line change is slow and, for private work, wrong. A registry running as a plain container on the same Docker network as the kind nodes lets docker push and a pod's image: field both point at localhost:5001 with no cloud account involved.

The one non-obvious wire-up

The registry container and the kind nodes have to be on the same Docker network, and containerd on each node needs a mirror rule telling it "when you see localhost:5001, actually go to kind-registry:5000." That's the containerdConfigPatches block in infra/kind-cluster.yaml.

registry reachable from inside a node
$ docker exec orderflow-control-plane curl -s http://kind-registry:5000/v2/_catalog
{"repositories":[]}   → later: ["inventory","orders"]
03

Namespaces

A namespace is not a VM, a network boundary, or a security boundary by itself — it's a naming scope. Two Deployments called orders can coexist if they're in different namespaces. On its own, that's all a namespace guarantees.

What makes a namespace also a network boundary is a separate object — NetworkPolicy — attached to it. Namespaces are the unit that policy selects on (namespaceSelector), which is why the two ideas get talked about together even though they're independently optional.

Four namespaces exist so far, one per concern:

NamespaceHoldsWhy separated
ordersorders Deployment + ServiceIndependent scale/restart lifecycle from inventory
inventoryinventory Deployment + 5 Service-type demosSame — and it's the namespace the Service-type exercises live in
dataPostgresShared by both app namespaces; kept separate so its own NetworkPolicy is written once
consolenginx serving the checkout consoleA completely different kind of workload (static assets, not a JVM API)
04

The CNI, NetworkPolicy, and why Calico got swapped in

This is the one genuine surprise of Phase 0 — worth understanding properly rather than skimming past.

Every Kubernetes cluster needs a CNI (Container Network Interface) plugin — the thing that actually gives each pod an IP address and wires up routing between pods. kind ships one by default, called kindnetd. It does the basic job (pods get IPs, pods can reach each other) but it implements none of the NetworkPolicy API — it's not that policies are ignored quietly on purpose, it's that kindnetd never registered itself as something that enforces them at all.

What this meant in practice

The very first version of this cluster had every NetworkPolicy in this repo applied cleanly — kubectl apply succeeded, kubectl get networkpolicy listed them all — and none of it did anything. A pod in console could have reached Postgres directly with zero errors, despite a "default-deny-all" policy sitting right there in the data namespace.

The fix: recreate the cluster with disableDefaultCNI: true, then install Calico — an open-source CNI that does implement NetworkPolicy (via Linux iptables rules it programs on every node, keyed to each pod's IP). This is why infra/kind-cluster.yaml sets podSubnet: 192.168.0.0/16 — that's Calico's own default pod IP range, matched so no extra config is needed on Calico's side.

The default-deny + explicit-allow shape

Every namespace gets a default-deny-all policy first (policyTypes: [Ingress, Egress], empty selector = applies to every pod, no rules = nothing is allowed). Then narrow policies add back exactly the traffic that's supposed to exist. This is deliberately the opposite of "allow everything, block the bad stuff" — with default-deny, a namespace you forget to write a rule for is safe by default, not open by accident.

A pod in orders trying to reach an arbitrary external address
      (not inventory, not postgres, not DNS) on port 30080:
$ kubectl -n orders exec orders-xxx -- curl -m5 http://172.20.0.3:30080/checkout
command terminated with exit code 28   ← timeout, exactly what default-deny egress does

$ docker exec orderflow-control-plane curl -m5 http://localhost:30080/checkout
{"id":"a455...","status":"RESERVED", ...}   ← same port, from the node's own network (not a pod, not policed)

That pair is worth sitting with: identical destination, identical port. One request comes from inside a pod (subject to Calico's enforcement) and times out. The other comes from the node's own host network namespace (not a pod, so no NetworkPolicy applies to it at all) and succeeds instantly. Same cluster, same second — the only variable is which network namespace the request originates from.

05

orders & inventory: the code-level decisions

Each of these exists because of a specific way the "obvious" version breaks. Concrete before/after, not abstract principle.

G1 — atomic stock reservation (no overselling)

The naive version

read stock → check enough? → write stock-qty. Two requests can both read "25 available" before either writes — both pass the check, both decrement, stock goes negative.

What's actually deployed

One SQL statement: UPDATE stock SET qty = qty - :n WHERE qty >= :n. The check and the write happen atomically inside Postgres — there's no gap between them for a second request to land in.

15 concurrent requests against a 25-unit SKU
8x  success (25 → 22 → 19 → ... → 1)
7x  INSUFFICIENT_STOCK at remaining=1, every time
final stock: 1   — never negative, across real concurrency, not a single-threaded test

G2 — idempotent reserve/release

The scenario

orders calls inventory. The response gets lost on the way back (network blip, or — starting Phase 4 — Istio's own retry policy). orders retries. Without protection, that's two decrements for one logical reservation.

What's actually deployed

Every reserve/release call carries an Idempotency-Key header. inventory checks a table keyed on that value before touching stock — a key it's seen before returns the stored result instead of mutating anything again.

same Idempotency-Key, sent twice
{"remaining":993,"success":true, ...}
{"remaining":993,"success":true, ...}   ← identical, not 988 — no second decrement happened

The rest, briefly

GapWhat breaks without it
G8 — probesKubernetes can't tell a hung pod from a healthy one, and sends traffic to a pod that isn't ready yet during startup
G9 — anti-affinityNothing stops 3 replicas landing on the same node — one node failure would then take out every replica at once

07

LoadBalancer & MetalLB, in depth

This is the one exercise with a real, worth-understanding limitation — not a mistake, a property of running kind on Docker Desktop for Mac.

On a real cloud, setting type: LoadBalancer makes Kubernetes call out to the cloud provider's API ("give me a real external IP and route it to these pods"). kind has no cloud provider to call — which is why, out of the box, a LoadBalancer Service on kind just sits at <pending> forever.

MetalLB is an open-source project that plays the role of "the cloud provider" for bare-metal or local clusters. It watches for LoadBalancer Services and, in the simplest mode (Layer 2), picks an IP from a configured pool and has one node announce "that IP is mine" over ARP — the same mechanism a machine on any Ethernet network uses to say "traffic for this IP should come to me."

  • Installed MetalLB (controller + a speaker DaemonSet, one per node).
  • Gave it a pool: 172.20.255.200-250 — a slice of the kind Docker network's own subnet that Docker's own IP allocator doesn't hand out to containers.
  • Created inventory-lb with type: LoadBalancer.
    • the IP assignment itself — this part worked exactly as intended
    NAME           TYPE           CLUSTER-IP    EXTERNAL-IP        PORT(S)
inventory-lb   LoadBalancer   10.96.32.44   172.20.255.200     8080:31200/TCP

speaker log: "service has IP, announcing" pool=kind-pool protocol=layer2

    That's the real Kubernetes-level lesson: a controller watching Service objects and assigning real IPs from a pool is exactly what happens on AWS/GCP too, just with a different controller underneath. But the actual packets never arrived:

    ARP table on the node that announced the IP
    $ ip neigh show | grep 172.20.255.200
(nothing — no entry, ever)

$ curl -m5 http://172.20.255.200:8080/...
curl: (28) Operation timed out
    Why, specifically

    Docker Desktop for Mac runs every container inside one Linux VM and emulates the "bridge network" containers sit on. Gratuitous ARP announcements — the mechanism MetalLB's Layer 2 mode depends on — don't reliably propagate across that emulated bridge the way they do on a real Linux host's bridge. The control-plane side (MetalLB deciding and announcing an IP) is 100% real Kubernetes behavior; the data-plane side (that IP actually being reachable) is where this specific laptop's virtualization falls short. On a native Linux Docker host, or a real cloud LoadBalancer, both sides work.

    Everything above, as one request: opening the checkout console and clicking "Place order."

  Browser->>Console: GET /  (port-forward :18090)

  Browser->>Console: POST /checkout {sku, quantity}

  Note over Console,Orders: allowed by allow-console-egress-to-orders

  Orders->>Inventory: POST /stock/{sku}/reserve
    Idempotency-Key: 
  Note over Orders,Inventory: allowed by allow-orders-egress-to-inventory
  Inventory->>PG: UPDATE stock SET qty=qty-:n WHERE qty>=:n
  Note over Inventory,PG: allowed by allow-inventory-egress-to-postgres
  PG-->>Inventory: 1 row updated (or 0 = insufficient)
  Inventory-->>Orders: 200 {success, remaining, handledByPod}

  Orders->>PG: INSERT order (status=RESERVED/REJECTED)
  Note over Orders,PG: allowed by allow-orders-egress-to-postgres
  Orders-->>Console: 201 {id, status, handledByPod}
  Console-->>Browser: same JSON, browser renders it

  loop every 2s, 5x
    Browser->>Console: GET /orders/{id}
    Console->>Orders: proxy_pass
    Orders->>PG: SELECT order
    Orders-->>Console: current status
    Console-->>Browser: handledByPod may differ each time
  end

    Every hop labeled with the specific NetworkPolicy that permits it — delete any one of those policies and that exact hop starts timing out, nothing else.

    The polling loop at the bottom is deliberate: each poll can land on a different orders pod (3 replicas, load-balanced by the ClusterIP Service), so handledByPod changing between polls on screen is the load-balancing behavior from section 1, now visible in a browser instead of a terminal.

    A Deployment doesn't manage pods directly — it manages a ReplicaSet, which is the thing actually watching and maintaining the replica count. Applying a change to a Deployment creates a new ReplicaSet and scales the old one to zero; that hand-off is how rolling updates work.

    The fast way to browse all of this: k9s

    Typing kubectl get pods -n X repeatedly gets old. k9s is a full-screen terminal UI over the same API: :pods jumps to the pod list, arrow keys navigate, l tails logs on the selected pod, d describes it, s shells into it, :ns switches namespace.
